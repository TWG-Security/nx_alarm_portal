Block banned addresses at Cloudflare

Without this, a banned address is refused by the portal itself. With it, each ban is also added to Cloudflare as an IP Access Rule, so the attacker's traffic stops at Cloudflare and never reaches the tunnel. Unbanning, allowlisting and expiry remove the rule again. Only rules the portal made are ever removed (their note starts with twg-alarm-portal auto-ban). If Cloudflare is down or the token is wrong, bans still work locally and the error shows here.

Getting the token and Zone ID

  1. Sign in at dash.cloudflare.com and click the domain twgsecurity.net.
  2. On the Overview page, find Zone ID in the right-hand column (scroll down a little). Click Click to copy and paste it above.
  3. Top right, click the person icon → My Profile → API Tokens (left menu) → Create Token.
  4. At the bottom, next to Create Custom Token, click Get started.
  5. Token name: alarm portal edge bans.
  6. Permissions: pick Zone → Firewall Services → Edit.
  7. Zone Resources: Include → Specific zone → twgsecurity.net.
  8. Click Continue to summary → Create Token, then Copy the token and paste it above. Cloudflare shows it only once.
  9. Tick Push bans to Cloudflare, click Save, then Test connection. It should say "Connected".

Who must use two-step sign-in

With two-step sign-in, a password alone isn't enough: people also type a code from an authenticator app on their phone, or use a passkey. People who must use it but haven't set it up are walked through it at their next sign-in (it takes a minute; nobody is locked out). People already signed in stay signed in.

Passkeys only work at https://alarmportal.twgsecurity.net; on the LAN address the code from the app is used.

How long people stay signed in

An open portal page talks to the server all the time, so a monitoring screen that's left open never counts as inactive and stays signed in. These limits are about browsers that were closed, and optional stricter rules.

Using a Google Workspace mailbox

Sign in with Google

Adds a Sign in with Google button to the sign-in page. It only signs in people who already have a portal account with that (Google-verified) email; nobody is created. Google's own sign-in, including its 2-Step Verification, replaces the portal's authenticator-app step. Password expiry still applies.

Leave empty to allow any Google account that matches a portal user. Customers' users can use their own Google accounts too.

Getting the client ID and secret

  1. Go to console.cloud.google.com, signed in with a TWG Google Workspace admin account. Pick (or create) a project, e.g. Alarm Portal.
  2. Left menu → APIs & Services → OAuth consent screen (or Google Auth Platform): user type External (so customers' Google accounts work; Internal limits it to TWG), app name TWG Alarm Portal, support email, then save. Under Data access/Scopes nothing extra is needed (email and profile are basic).
  3. APIs & Services → Credentials → Create credentials → OAuth client ID → type Web application, name Alarm portal.
  4. Authorized JavaScript origins → Add URI:
  5. Authorized redirect URIs → Add URI:
  6. Click Create, copy the Client ID and Client secret into the boxes above, tick the box and Save.
  7. For External apps, publish the consent screen (Publish app) so people outside the test-user list can sign in.
